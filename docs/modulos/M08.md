## 1. Objetivo
Guardar el historial de cada conversación de forma persistente y devolver los **últimos N mensajes** (`HISTORY_WINDOW_N`) en orden cronológico, para que el servicio RAG (M9) reformule las preguntas de seguimiento. Cubre el requisito del caso de memoria conversacional por `conversation_id`. Además, cada mensaje guarda las métricas que usará la analítica de M11.

## 2. Alcance
- Incluye:
  - interfaz `ConversationRepository` (Repository) y dos implementaciones: SQLite con SQLAlchemy 2 y en memoria;
  - las tablas del plan (`conversations`, `messages`) con fuentes, latencias, score, `no_answer`, tokens y valoración;
  - contrato para un `conversation_id` inexistente (ADR-013);
  - `ComponentFactory.create_conversation_repository()` y el comando de solo lectura `history`.
- No incluye:
  - conectar el historial con `QueryRewriter` y `AnswerGenerator`, ni escribir mensajes desde una pregunta real: es el `RAGService` (Facade) de M9;
  - endpoints de la API (M9) ni analítica (M11);
  - migraciones de esquema (L-13).

## 3. Diseño
- Componentes / archivos creados:
  - `src/rag_bbva/memory/models.py`: `Conversation`, `Message`, `MessageMetrics` (pydantic, inmutables), `title_from_question`, `utc_now`. `Message.as_chat_message()` devuelve el formato `{"role", "content"}` que recibe el reformulador de M7.
  - `src/rag_bbva/memory/repository.py`: interfaz `ConversationRepository` (`create_conversation`, `get_conversation`, `list_conversations`, `add_message`, `get_messages`, `get_last_n`, `set_feedback`, `require_conversation`), validaciones comunes e `InMemoryConversationRepository`.
  - `src/rag_bbva/memory/sql_repository.py`: `SqlAlchemyConversationRepository` (`from_path`, `in_memory`, `close`). Crea las tablas si faltan, activa las claves foráneas de SQLite, guarda las fechas en UTC y traduce `SQLAlchemyError` a `HistoryError`.
  - `src/rag_bbva/exceptions.py`: `ConversationNotFoundError` y `MessageNotFoundError`, subclases de `HistoryError`.
  - `src/rag_bbva/cli.py`: `history` (lista conversaciones) y `history <ID> [--last N]` (mensajes; `--last` usa `get_last_n`).
- Esquema (igual al del plan, verificado por `test_crea_las_tablas_del_plan`):
  - `conversations(id, created_at, updated_at, title)`: `id` UUID4 en texto; índice por `updated_at`.
  - `messages(id, conversation_id, role, content, created_at, sources_json, retrieval_ms, rerank_ms, llm_ms, total_ms, top_score, no_answer, prompt_tokens, completion_tokens, feedback)`: `id` autoincremental; FK a `conversations` con `ON DELETE CASCADE`; índice por `conversation_id`.
- Patrones de diseño aplicados:
  - **Repository:** el servicio habla con `ConversationRepository` sin saber de SQL. Las pruebas de contrato corren contra tres variantes (memoria, SQLite en memoria y SQLite en archivo), así que las dos implementaciones cumplen lo mismo.
  - **Factory:** `ComponentFactory.create_conversation_repository()` crea el repositorio desde `HISTORY_DB_PATH`.
- Configuración nueva (`.env`): ninguna. Se usan `HISTORY_DB_PATH` y `HISTORY_WINDOW_N`, que ya existían desde M0.
- Dependencia nueva: `sqlalchemy>=2.0,<2.2` (instalada 2.1.3), en su propio commit (ADR-007).

## 4. Decisiones y supuestos
- **ADR-013** — un `conversation_id` desconocido **se informa, no se crea**:
  - el servidor crea la conversación y su ID (UUID4);
  - leer o escribir en un ID inexistente lanza `ConversationNotFoundError` (404 en la API de M9).
  - Motivo: un ID mal copiado no debe abrir en silencio una conversación vacía, sin el contexto que el usuario cree tener.
  - **Aceptado por Juan Felipe** en la revisión del módulo (el plan dejaba abiertas las dos opciones).
- **S-05** actualizado con ese contrato (`00_VISION_GENERAL.md §9`).
- **Orden por `id` autoincremental, no por hora:** dos mensajes con la misma hora (p. ej. escritos en el mismo milisegundo) no se desordenan. Lo prueba `test_orden_por_insercion_aunque_coincida_la_hora` con un reloj fijo.
- **Título = primera pregunta del usuario** (una línea, máx. 80 caracteres); un título explícito no se reemplaza.
- **Ventana `n`:** `n=0` devuelve vacío; `n<0` es un error (`HistoryError`). `HISTORY_WINDOW_N` ya valida `ge=0`.
- **Valoración:** `up`, `down` o `None` (quitarla). Se guarda en el mismo mensaje, como pide el plan.
- **Fechas en UTC:** SQLite no guarda zona horaria; se escriben en UTC y se leen con `tzinfo=UTC`.

## 6. Evidencia manual
Persistencia entre **procesos distintos**: un proceso escribe y otros cuatro leen con la CLI. Se usó una base en el scratchpad (`HISTORY_DB_PATH=…/evidencia_m08/history.db`) para no dejar datos de prueba en `data/history/`, que usarán M9 y M11. Sin LLM: los textos del asistente son de ejemplo.

```

feedback: up
== Proceso 2: lista ==
Conversaciones (2, más recientes primero):
  9ef6836f-0500-49ea-8033-fea29bdf7fc7  2026-10-03T14:55:54+00:00  ¿Cómo pago el 4 por mil?
  220fca96-f9b6-49f5-ab90-05c3a4e6b0c9  2026-10-03T14:55:54+00:00  ¿Qué es un CDT?
== Proceso 3: get_last_n(A, 6) ==
Conversación 220fca96-f9b6-49f5-ab90-05c3a4e6b0c9 · ¿Qué es un CDT?
```

(Se omiten las líneas de log JSON `Historial de conversaciones en …`.)

Qué muestra:
- A tiene 8 mensajes (4 turnos); `--last 6` devuelve los mensajes 3 a 8 en orden cronológico, sin mezclar el de B.
- B aparece primero porque se escribió después.
- La valoración `up` del mensaje 8 se escribió en el proceso 1 y se lee en otro proceso.
- `--last 0` no devuelve mensajes; un ID inexistente sale con código 1 y un mensaje claro.

## 7. Problemas encontrados y solución
- **Conteo de pruebas:** al cerrar M7 se reportó "401 passed sin integración". Hoy en `main` la suite rápida da 397: la diferencia son las 4 pruebas `slow`, que el 401 incluía (`-m "not integration"`). Con M8: 401 + 68 = 469 (sin integración), 397 + 68 = 465 (rápidas). No era un error de pruebas, sino de qué filtro se citaba.
- **Commit de pruebas antes del lint:** el commit `test(memory)` se hizo en paralelo con `ruff check`, que marcó una línea larga. Como no estaba publicado, se corrigió con `ruff format` y `git commit --amend`.

## 8. Pendientes / deuda técnica
- **M9:** el `RAGService` usará `get_last_n(id, HISTORY_WINDOW_N)` → `as_chat_message()` → `QueryRewriter`; después guardará la pregunta y la respuesta con sus métricas. La API traducirá `ConversationNotFoundError` y `MessageNotFoundError` a 404.
- **L-13:** sin migraciones de esquema (Alembic si cambia el esquema) y SQLite pensado para una sola instancia de la API.
- Sin borrado de conversaciones ni retención: no lo pide el caso. Las preguntas quedan en texto plano en el volumen de datos.
