## 1. Objetivo
Dar a los usuarios internos una interfaz conversacional sencilla sobre la API de M9 (F4):
- chatear con memoria;
- ver las fuentes citadas;
- valorar respuestas;
- retomar conversaciones;
- entender el estado del servicio.

Incluye una CLI de respaldo para conversar sin navegador.

## 2. Alcance
- Incluye:
  - UI Streamlit que consume la API por HTTP (`ApiClient`, `API_BASE_URL`);
  - comandos `ui` y `chat`;
  - pruebas con respx, `AppTest` y `CliRunner`;
  - guion de prueba ejecutado contra la API real y lista de capturas.
- No incluye:
  - streaming de la respuesta (L-15);
  - usuarios o autenticación (L-14);
  - panel de analítica (M11);
  - Docker de la UI (M12).

## 3. Diseño
- Componentes / archivos creados:
  - `src/rag_bbva/ui/api_client.py`: `ApiClient` (`chat`, `list_conversations`, `get_conversation`, `send_feedback`, `health`) y modelos que reflejan el JSON de la API.
    - Todo error → `ApiClientError(message, status, detail)`.
    - Timeout → "La respuesta está tardando demasiado…".
    - Sin conexión → "No se pudo conectar con la API en … Inicie `serve` y revise API_BASE_URL".
    - Un 503 de `/health` no es error: es el reporte degradado.
  - `src/rag_bbva/ui/render.py`: presentación sin Streamlit, probada por separado.
    - `link_citations`: [n] → enlace;
    - `escape_markdown`: `$` → `\$`, porque Streamlit interpreta `$…$` como LaTeX y las respuestas traen montos como "$151.994";
    - `source_lines`, `friendly_error` (404/422/503), `health_lines`, `detail_lines` y `shorten`;
    - el texto `AVISO`.
  - `src/rag_bbva/ui/app.py`: la página.
    - Estado en `st.session_state`: `api_client`, `conversation_id`, `messages` y `error`.
    - Las acciones (nueva conversación, retomar, votar) son callbacks.
    - Al enviar una pregunta: spinner → `ApiClient.chat` → `st.rerun()`.
  - `src/rag_bbva/cli.py`:
    - `ui`: `python -m streamlit run …/ui/app.py` con `--host`, `--port` y `--api-url`, en modo headless y sin telemetría;
    - `chat [--conversation-id X]`: bucle en la terminal sobre `RAGService`, como pide el plan.
  - `ApiClientError` en `exceptions.py`.
- **La UI no importa el núcleo:** `test_la_ui_no_importa_el_nucleo` recorre las importaciones de `ui/*.py` y falla si alguna apunta a `services`, `retrieval`, `llm`, `indexing`, `memory`, `api`, `scraping` o `processing`. Sí usa `rag_bbva.config` (configuración, CLAUDE.md) y `rag_bbva.exceptions`.
- Patrones de diseño:
  - **inyección de dependencias:** la app toma el cliente de `st.session_state`; los tests ponen uno falso antes de ejecutar;
  - el cliente HTTP aísla la UI de la API, que es la frontera del sistema.
- Configuración nueva (`.env`): `API_BASE_URL=http://127.0.0.1:8000`, `UI_HOST=127.0.0.1`, `UI_PORT=8501`, `UI_REQUEST_TIMEOUT_SECONDS=180`.
- Dependencia nueva: `streamlit>=1.40,<2` (instalada 1.65.0), en su propio commit (ADR-007).

## 4. Decisiones y supuestos
- **Timeout de 180 s:** en M9, con `gemini-3.1-flash-lite` saturado, un turno real tardó ~150 s (503 + reintento + timeout de 60 s del LLM). Un timeout corto mostraría errores a respuestas que sí llegan.
- **Pregunta fallida = no se guarda:** si la API responde con error, la pregunta no queda en el chat (coherente con el turno atómico, ADR-014). El error la cita, recortada a 80 caracteres, para reintentarla.
- **404 al continuar:** la siguiente pregunta abre una conversación nueva, en vez de insistir con un ID que no existe.
- **Lista de conversaciones:** título + fecha y hora UTC. Tres conversaciones con la misma primera pregunta eran indistinguibles (hallazgo del guion, §7).
- **Sin streaming:** la API de M9 responde completo. Exponer SSE quedaría para una mejora (L-15).
- **CLI `chat` sobre `RAGService` y no sobre la API**, como pide el plan: sirve aunque la API no esté levantada.

## 7. Problemas encontrados y solución
- **El guion retomó la conversación equivocada** (error del script, no de la app): `at.button[1]` buscaba el botón "Retomar por ID" por índice, pero con conversaciones en la lista ese índice era el primer botón de la lista (conversación C). La pregunta A4 se respondió dentro de C, que quedó con un turno de más en el historial real (`data/history/history.db`). El script ahora busca los botones por etiqueta y verifica que se retomó A. La prueba unitaria `test_retomar_por_id…` ahora tiene conversaciones en la lista: con la lista vacía de antes, el índice coincidía por casualidad. Se repitió la parte 2 (§6.2, R1–A4).
- **Lista de conversaciones indistinguible:** 3 conversaciones con la misma primera pregunta. Se agregó la fecha y hora (UTC) a la etiqueta, con prueba.
- **Error con la pregunta completa:** la pregunta de 1001 caracteres llenaba el mensaje de error. Ahora se cita recortada (`shorten`, 80 caracteres), con prueba.
- **Texto del aviso en la CLI:** el banner de `chat` usaba otra redacción; la prueba lo detectó y ahora reutiliza `AVISO`.
- **Latencia del LLM gratuito:** los turnos tardaron 4,6–35,7 s por la lentitud de `gemini-3.1-flash-lite` en ese momento (en M9 había respondido en 1–2 s). Por eso el timeout de la UI es de 180 s y hay un indicador de espera.
