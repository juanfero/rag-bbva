## 1. Objetivo
Dar a los usuarios internos una interfaz conversacional sencilla sobre la API de M9 (F4):
- chatear con memoria;
- ver las fuentes citadas;
- valorar respuestas;
- retomar conversaciones;
- entender el estado del servicio.

Incluye una CLI de respaldo para conversar sin navegador.

## 2. Alcance
- Incluye:
  - UI Streamlit que consume la API por HTTP (`ApiClient`, `API_BASE_URL`);
  - comandos `ui` y `chat`;
  - pruebas con respx, `AppTest` y `CliRunner`;
  - guion de prueba ejecutado contra la API real y lista de capturas.
- No incluye:
  - streaming de la respuesta (L-15);
  - usuarios o autenticación (L-14);
  - panel de analítica (M11);
  - Docker de la UI (M12).

## 3. Diseño
- Componentes / archivos creados:
  - `src/rag_bbva/ui/api_client.py`: `ApiClient` (`chat`, `list_conversations`, `get_conversation`, `send_feedback`, `health`) y modelos que reflejan el JSON de la API.
    - Todo error → `ApiClientError(message, status, detail)`.
    - Timeout → "La respuesta está tardando demasiado…".
    - Sin conexión → "No se pudo conectar con la API en … Inicie `serve` y revise API_BASE_URL".
    - Un 503 de `/health` no es error: es el reporte degradado.
  - `src/rag_bbva/ui/render.py`: presentación sin Streamlit, probada por separado.
    - `link_citations`: [n] → enlace;
    - `escape_markdown`: `$` → `\$`, porque Streamlit interpreta `$…$` como LaTeX y las respuestas traen montos como "$151.994";
    - `source_lines`, `friendly_error` (404/422/503), `health_lines`, `detail_lines` y `shorten`;
    - el texto `AVISO`.
  - `src/rag_bbva/ui/app.py`: la página.
    - Estado en `st.session_state`: `api_client`, `conversation_id`, `messages` y `error`.
    - Las acciones (nueva conversación, retomar, votar) son callbacks.
    - Al enviar una pregunta: spinner → `ApiClient.chat` → `st.rerun()`.
  - `src/rag_bbva/cli.py`:
    - `ui`: `python -m streamlit run …/ui/app.py` con `--host`, `--port` y `--api-url`, en modo headless y sin telemetría;
    - `chat [--conversation-id X]`: bucle en la terminal sobre `RAGService`, como pide el plan.
  - `ApiClientError` en `exceptions.py`.
- **La UI no importa el núcleo:** `test_la_ui_no_importa_el_nucleo` recorre las importaciones de `ui/*.py` y falla si alguna apunta a `services`, `retrieval`, `llm`, `indexing`, `memory`, `api`, `scraping` o `processing`. Sí usa `rag_bbva.config` (configuración, CLAUDE.md) y `rag_bbva.exceptions`.
- Patrones de diseño:
  - **inyección de dependencias:** la app toma el cliente de `st.session_state`; los tests ponen uno falso antes de ejecutar;
  - el cliente HTTP aísla la UI de la API, que es la frontera del sistema.
- Configuración nueva (`.env`): `API_BASE_URL=http://127.0.0.1:8000`, `UI_HOST=127.0.0.1`, `UI_PORT=8501`, `UI_REQUEST_TIMEOUT_SECONDS=180`.
- Dependencia nueva: `streamlit>=1.40,<2` (instalada 1.65.0), en su propio commit (ADR-007).

## 4. Decisiones y supuestos
- **Timeout de 180 s:** en M9, con `gemini-3.1-flash-lite` saturado, un turno real tardó ~150 s (503 + reintento + timeout de 60 s del LLM). Un timeout corto mostraría errores a respuestas que sí llegan.
- **Pregunta fallida = no se guarda:** si la API responde con error, la pregunta no queda en el chat (coherente con el turno atómico, ADR-014). El error la cita, recortada a 80 caracteres, para reintentarla.
- **404 al continuar:** la siguiente pregunta abre una conversación nueva, en vez de insistir con un ID que no existe.
- **Lista de conversaciones:** título + fecha y hora UTC. Tres conversaciones con la misma primera pregunta eran indistinguibles (hallazgo del guion, §7).
- **Sin streaming:** la API de M9 responde completo. Exponer SSE quedaría para una mejora (L-15).
- **CLI `chat` sobre `RAGService` y no sobre la API**, como pide el plan: sirve aunque la API no esté levantada.

## 7. Problemas encontrados y solución
- **El guion retomó la conversación equivocada** (error del script, no de la app): `at.button[1]` buscaba el botón "Retomar por ID" por índice, pero con conversaciones en la lista ese índice era el primer botón de la lista (conversación C). La pregunta A4 se respondió dentro de C, que quedó con un turno de más en el historial real (`data/history/history.db`). El script ahora busca los botones por etiqueta y verifica que se retomó A. La prueba unitaria `test_retomar_por_id…` ahora tiene conversaciones en la lista: con la lista vacía de antes, el índice coincidía por casualidad. Se repitió la parte 2 (§6.2, R1–A4).
- **Lista de conversaciones indistinguible:** 3 conversaciones con la misma primera pregunta. Se agregó la fecha y hora (UTC) a la etiqueta, con prueba.
- **Error con la pregunta completa:** la pregunta de 1001 caracteres llenaba el mensaje de error. Ahora se cita recortada (`shorten`, 80 caracteres), con prueba.
- **Texto del aviso en la CLI:** el banner de `chat` usaba otra redacción; la prueba lo detectó y ahora reutiliza `AVISO`.
- **Latencia del LLM gratuito:** los turnos tardaron 4,6–35,7 s por la lentitud de `gemini-3.1-flash-lite` en ese momento (en M9 había respondido en 1–2 s). Por eso el timeout de la UI es de 180 s y hay un indicador de espera.

## 10. Ajustes derivados de M9
Pedidos en la revisión de M9 (2026-10-03), antes de cerrar M10. La lista de capturas y el guion ya los tiene Juan Felipe (§6.2 y §6.4).

### 10.1 Latencia (ADR-017 ampliada, L-11)
- **Timeout por llamada `LLM_TIMEOUT_SECONDS=20`** (antes 60), con **tope de reloj**. El timeout de httpx es por operación de lectura, no total: en la primera corrida de esta evidencia, una petición tardó 39 s en devolver un 503 con timeout=20. Cada intento corre en un hilo y se espera como máximo `min(20 s, plazo restante)`; si se vence, cuenta como timeout.
- **Respaldo también ante timeout y 5xx** (`LLMUnavailableError`), tras **un** reintento del principal. El 429 de cupo diario pasa al respaldo sin reintento. Errores de clave o de modelo inexistente: sin respaldo.
- **Presupuesto del turno `LLM_TURN_BUDGET_SECONDS=45`** (`llm/budget.py`, una `ContextVar` que fija `RAGService.ask`):
  - cada llamada usa el plazo restante como tope;
  - las esperas entre reintentos no lo superan;
  - sin plazo no se intenta el respaldo.
  - Si se agota: 503 *"El servicio de respuestas está lento en este momento. Intenta de nuevo en unos minutos."* y el turno no se guarda.
- `UI_REQUEST_TIMEOUT_SECONDS`: 180 → 60 s.
- **Pruebas** (`test_latencia.py`, 20):
  - respaldo tras un reintento ante timeout, 503, 500 y 429 por minuto; 429 diario sin reintento;
  - sin respaldo ante 401, 400 de clave inválida y 404;
  - clasificación de los errores;
  - el timeout que llega a la petición es 20 s, o el plazo restante dentro de un turno;
  - sin plazo no se llama al LLM; las esperas de backoff no pasan del plazo; sin plazo no se intenta el respaldo;
  - turno que excede el presupuesto → `LLMBudgetExceededError` y nada guardado; la API responde 503 con el mensaje;
  - la fábrica da 1 reintento al principal;
  - **tope de reloj** con un servidor simulado que contesta en 2 s sin que httpx lo corte: con timeout de 0,2 s, pasa al respaldo en < 1 s; sin respaldo da timeout en < 1 s; con plazo de 0,3 s manda el plazo.
- Pruebas ajustadas al nuevo diseño:
  - `test_settings_defaults` (20 s);
  - la de M9 que contaba el timeout entre los errores "sin respaldo", que ahora cubre solo clave y modelo;
  - `strip_abstention` (§10.2).

- **Para la sustentación** conviene una clave con cupo en `gemini-2.5-flash` (proyecto nuevo, L-11), que respondió en ~1 s.
- **`.env` local:** tenía `LLM_TIMEOUT_SECONDS=60`, copiado del ejemplo viejo, y pisaba el nuevo valor por defecto. Se cambió solo esa variable (no secreta) a 20, sin leer ni imprimir las claves. `.env` sigue ignorado.

### 10.2 Marca de abstención: solo al inicio
La corrida 2 mostró una respuesta útil (3 citas) que terminaba con `[SIN_INFO] No encontré información… sobre otros costos`. `strip_abstention` trataba la marca en cualquier posición como abstención. Ahora solo es abstención si la respuesta **empieza** con la marca, que es lo que pide el prompt; una marca a mitad o al final se borra sin marcar `no_answer`. ### 10.4 Hallazgo: la limpieza de M3 pierde celdas repetidas en tablas (pendiente de decisión)
Al verificar n13 se vio que el texto limpio de la tabla de tasas tiene **6 valores por fila y el HTML 7**: `0,15 | 7,60 | 8,15 | 8,55 | 8,75 | 8,75 | 8,85`.
- **Causa:** `normalize_text` (M3) elimina **bloques consecutivos idénticos**, una regla pensada para el texto duplicado de las versiones de escritorio y móvil. Cada celda queda como un bloque propio, así que dos celdas vecinas con el mismo valor se funden y la fila se corre una columna: el texto limpio atribuye 8,85 % a 360–539 días cuando el sitio dice 8,75 %. El 7,60 % de n13 está antes del corrimiento y es correcto.
- **Alcance** (sobre los 597 documentos conservados): 137 documentos tienen tablas (357 tablas). **22 tablas en 10 páginas** tienen celdas vecinas idénticas, con **189 filas** afectadas. **147 están en `/personas/tarifario/cuentas`** (tarifas); el resto, en `/negocios/.../cdt` y en páginas de necesidades.
- **Además**, las tablas se aplanan a una celda por línea y se pierde la estructura de filas y columnas: el LLM infiere la columna por posición.
- **Propuesta** (no aplicada; requiere re-limpiar, re-fragmentar y re-indexar, ~2 min con la caché, y cambia los datos de las evidencias):
  1. Mínima: no deduplicar bloques consecutivos cortos (< 60 caracteres).
  2. Mejor: extraer cada tabla como filas Markdown (`| Monto | 60-89 días | 90-119 días | … |`), para que el LLM lea la estructura y no pueda correr columnas; con pruebas sobre la tabla real del CDT y del tarifario.
