## 1. Objetivo
Unir las piezas de M5–M8 en un servicio conversacional usable por HTTP:
- una fachada (`RAGService`) que responde una pregunta dentro de una conversación, con memoria;
- una API FastAPI para chatear, consultar el historial, valorar respuestas y ver el estado del sistema.

Cubre F4 (interfaz conversacional, la parte de API) y los requisitos de memoria por `conversation_id` y de persistencia de métricas.

## 2. Alcance
- Incluye:
  - `RAGService` (Facade) con turno atómico (ADR-014);
  - pregunta autónoma en el prompt de los seguimientos (ADR-015);
  - API con `create_app`, `Depends`, lifespan con `warm_up`, manejadores de errores globales y validación;
  - `/health` sin gastar tokens;
  - comando `serve`;
  - SQLite seguro entre hilos.
- No incluye:
  - `/analytics` (M11);
  - la UI web (M10);
  - streaming por HTTP (el generador ya lo soporta; ver L-14);
  - autenticación (S-05, L-14);
  - Docker de la API (M12).

## 3. Diseño
- Componentes / archivos creados:
  - `src/rag_bbva/services/rag_service.py`: `RAGService` (`ask`, `warm_up`, `list_conversations`, `get_conversation`, `set_feedback`) y los modelos `ChatResult`, `SourceRef`, `Timings`, `TokenUsage`.
  - `src/rag_bbva/services/health.py`: `HealthChecker` y `HealthReport`.
    - Qdrant: `count()` de la colección; vacía o inexistente cuenta como caída.
    - SQLite: lee la conversación más reciente.
    - LLM: solo la configuración (proveedor, modelo y si hay clave). No llama a la API.
  - `src/rag_bbva/api/app.py`: `create_app(settings, *, service, health_checker, warm_up)`, las dependencias `get_rag_service`, `get_health_checker` y `get_app_settings`, el `lifespan` y las 5 rutas.
  - `src/rag_bbva/api/schemas.py`: `ChatRequest` (quita espacios de los extremos; vacía → 422), `FeedbackRequest`, salidas del historial y `ErrorResponse`.
  - `src/rag_bbva/api/errors.py`: manejadores globales (tabla en el docstring del módulo).
  - `ConversationRepository.add_turn` (memoria y SQLite): pregunta, respuesta y conversación nueva en una sola transacción.
  - `ComponentFactory.create_rag_service` / `create_health_checker`, `UnconfiguredLLMProvider` y el comando `serve`.
- Flujo de `ask(conversation_id | None, question)`:
  1. Si hay ID: `require_conversation` (404 antes de gastar tokens) y `get_last_n(id, HISTORY_WINDOW_N)`.
  2. `QueryRewriter.rewrite(question, historial)` según `QUERY_REWRITE_MODE`.
  3. `Retriever.retrieve(query)`: embedding, Qdrant top-20, cross-encoder, diversidad y umbral `no_answer`.
  4. `AnswerGenerator.generate(question, recuperación, pregunta_autónoma)`. Con `no_answer` no se llama al LLM.
  5. `add_turn(...)` con fuentes y métricas: latencias, `top_score`, `no_answer` y tokens de reformulación + respuesta.
- Qué se guarda por respuesta:
  - `llm_ms` es solo la generación;
  - `total_ms`, todo el turno salvo el guardado;
  - los tokens suman reformulación y respuesta (lo que cuesta el turno).
  - `rewritten_query` y el tiempo de reformulación van en la respuesta HTTP, pero no en la base: el esquema de M8 no tiene esas columnas y no hay migraciones (L-13).
- Patrones de diseño aplicados:
  - **Facade:** `RAGService` es el único punto de entrada; la API no conoce al retriever ni al LLM.
  - **Inyección de dependencias / app factory:** `create_app` recibe los componentes y las rutas los piden con `Depends`. Los tests pasan dobles o usan `dependency_overrides`.
  - **Factory:** `ComponentFactory` arma el servicio desde `Settings`.
  - **Repository:** `add_turn`, en las dos implementaciones.
  - **Null Object:** `UnconfiguredLLMProvider` deja arrancar la API sin clave; `/health` lo informa y cada pregunta responde 503 con el motivo.
- Concurrencia: endpoints `def` (FastAPI los corre en su threadpool). SQLite con `check_same_thread=False`, espera de 15 s ante bloqueos y modo WAL.
- Configuración nueva (`.env`): `API_HOST=127.0.0.1`, `API_PORT=8000`, `CHAT_QUESTION_MAX_CHARS=1000`.
- Dependencias nuevas (commit `build` propio, ADR-007): `fastapi>=0.115,<1` (instalada 0.142.2) y `uvicorn>=0.30,<1` (0.54.0).

## 4. Decisiones y supuestos
- **ADR-014 — Turno atómico** (pedido por Juan Felipe): nada se guarda hasta tener la respuesta.
  - Si falla el LLM, Qdrant o la base, no quedan preguntas sueltas ni conversaciones vacías.
  - Los turnos `no_answer` sí se guardan.
- **ADR-015 — Pregunta autónoma en el prompt de respuesta:** cambia la decisión de M7 de responder solo con la pregunta original.
  - Sin ella, el LLM recibía "¿y cuáles son los requisitos?" sin saber de qué producto.
  - El prompt de sistema no cambia; `PROMPT_VERSION` 2026-10-03.1. Sin reformulación, el prompt es idéntico al de M7.
  - **Aprobado por Juan Felipe** en la revisión del módulo.
- **ADR-013** aplicado: sin ID se crea la conversación (dentro de `add_turn`); un ID inexistente da 404.
- **Códigos HTTP:**
  - 503 para todo lo que depende de un servicio externo o de la configuración: LLM (incluido el cupo diario), Qdrant, SQLite y falta de clave.
  - 500 solo para lo inesperado.
  - El `detail` técnico del proveedor del LLM y de Qdrant **no** llega al cliente, solo al log.
- **Valoración solo de respuestas:** valorar el ID de una pregunta da 404 ("La respuesta no existe").
- **`/health`:**
  - 200 si todo está bien; 503 `degraded` si algo falla, para que Docker (M12) o un balanceador lo detecten sin leer el cuerpo.
  - Una colección vacía cuenta como caída: sin datos no hay respuestas.
- **API arranca sin clave del LLM:** se puede diagnosticar con `/health` en lugar de un proceso que muere al iniciar.
- **`API_HOST=127.0.0.1` por defecto:** sin autenticación, no se expone a la red por accidente (L-14).

## 7. Problemas encontrados y solución
- **Puerto 8000 ocupado** por un contenedor de otro proyecto: el servidor arrancó (warm-up 7,5 s) y uvicorn falló al enlazar el puerto (`[Errno 98] address already in use`). Se usó `--port 8010`; el README indica la opción.
- **Cupo diario de `gemini-2.5-flash` agotado** (L-11): el primer `/chat` dio 503 con el mensaje amigable. Se usó el modelo de respaldo solo para la evidencia.
- **El modo `:memory:` de qdrant-client lanza `ValueError`** al contar una colección inexistente; el adaptador de M5 solo traducía los errores del servidor. Lo encontró la prueba del lifespan. Se corrigió en el adaptador, con un mensaje de "ejecute ingest" también para el 404 del servidor.
- **Pruebas dependientes del entorno:** `test_health_ok` y `test_llm_sin_clave_503` fallaron en la corrida con `LLM_MODEL=gemini-3.1-flash-lite`. La configuración de prueba ahora ignora `.env` y fija los valores que se comprueban; no se cambió ninguna aserción. Se verificó con variables adversas (`LLM_MODEL`, `QDRANT_COLLECTION`, `HISTORY_WINDOW_N`, `QUERY_REWRITE_MODE`).

## 8. Pendientes / deuda técnica
- **Hallazgo — umbral en los seguimientos:** los turnos 3 y 4 quedaron como `no_answer` (`top_score` 1,44 en el 3) aunque el turno 2 ya había citado costos de escrituración y registro. El umbral se calibró con preguntas sueltas (M6, dentro de la muestra); con preguntas reformuladas más largas podría cortar de más. Lo debe medir el golden set de M13.
- `rewritten_query` y el tiempo de reformulación no se guardan en la base (sin columnas en el esquema de M8 y sin migraciones, L-13). Si M11 los necesita, habrá que agregar columnas con migración.
- Streaming por HTTP (SSE) para la UI de M10, si se decide exponerlo.
- M12: `API_HOST=0.0.0.0` en el contenedor y `healthcheck` sobre `/health`.

### 10.1 Umbral doble (ADR-016)
- `RERANK_HARD_MIN_SCORE=-3.0`, elegido con la distribución de M6:
  - las respondibles tienen mediana 4,44 y mínima −2,58 ("¿qué es el GMF o 4 por mil?");
  - las no respondibles, mediana −3,31.
  - Con −3,0, ninguna respondible queda debajo y 8 de 15 no respondibles se cortan sin LLM. El corte queda entre −3,31 (Davivienda) y −2,66 (prensa).
- La zona gris [−3,0; 1,6) llama al LLM. La marca `[SIN_INFO]` (reglas 4 y 5 del prompt de sistema) se quita del texto, también en streaming, y deja `no_answer=true`.
- `RetrievalResult` conserva `no_answer` (M6) y agrega `hard_no_answer` y `gray_zone`; `ChatResult` expone `gray_zone`; `search` muestra las tres zonas.
- Pruebas (`test_umbral_doble.py`, 25):
  - las cinco posiciones del score, incluidos los dos bordes;
  - sin umbral duro se comporta como M6;
  - sin reranker no hay umbrales;
  - la configuración rechaza un umbral duro mayor que el blando;
  - por debajo del duro no se llama al LLM; en la zona gris sí, y puede responder;
  - la marca → `no_answer` (también por encima del umbral);
  - `strip_abstention` y el filtro del streaming (marca partida en fragmentos);
  - el servicio guarda la abstención como `no_answer`.
- El snapshot del prompt se regeneró: el diff toca solo las reglas 4 y 5, y `PROMPT_VERSION` pasó a 2026-10-03.2.

### 10.2 Modelo de respaldo (ADR-017, Decorator)
- `LLMQuotaError` (subclase de `LLMError`): el proveedor la lanza solo ante un 429 de la API (cupo diario, o límite por minuto tras agotar los reintentos), también al abrir el streaming.
- `FallbackLLMProvider(primary, fallback)`: ante `LLMQuotaError` repite la llamada con el respaldo y registra `Cupo agotado en el modelo principal; responde el de respaldo` (con ambos modelos). El modelo que respondió llega a `ChatResult.model`. No se guarda en la base: el esquema de M8 no tiene la columna.
- La fábrica lo aplica si `LLM_FALLBACK_MODEL` no está vacío y es distinto de `LLM_MODEL`; `/health` informa `fallback_model`.
- Pruebas (+7 en `test_llm.py`):
  - el respaldo responde ante cupo agotado (`complete` y `stream`);
  - sin error no se usa;
  - clave inválida, modelo inexistente y timeout **no** activan el respaldo;
  - si el respaldo también agota el cupo, se informa;
  - con la API simulada, solo 429 es `LLMQuotaError` (401 y 404 no);
  - de punta a punta con el SDK: 429 de cupo diario para `gemini-2.5-flash` → 200 del respaldo, sin reintentar el cupo diario;
  - la fábrica no envuelve si el respaldo está vacío o es el mismo modelo.
- Pruebas existentes ajustadas al nuevo diseño, sin quitar comprobaciones: las de la fábrica desenvuelven el Decorator (`.primary`) y además verifican el respaldo; la de xAI usa `LLM_FALLBACK_MODEL=` (configuración documentada para xAI); `/health` incluye `fallback_model`.
